# 0027 包体预算

状态：已定 · 2026-10-21

## 实测（Release，iOS，未签名）

| 组成 | 大小 |
|---|---|
| `content.db` | 32.0 MB |
| 可执行文件（含 GRDB） | 6.4 MB |
| 图片（107 张） | 9.6 MB |
| 其余（plist 等） | < 0.1 MB |
| **合计** | **48 MB** |

App Store 走差分与切片后，用户实际下载还会更小。

## 决定

1. **预算：80 MB**（v1.0）。当前 48 MB，余量 32 MB。
2. **图片宽度上限 1600 px**，构建时自动降采样（显示宽度最多 720pt，2 倍屏够用）。
3. **不把 PNG 转 JPEG**。大图里有地图和带文字的截图，有损压缩会糊字；省 2–3 MB 不值这个代价。
4. **不做 DB 字段裁剪**。`pages` 20 MB + FTS 索引 10.8 MB 已经是紧凑形态，裁剪收益小于维护成本。

## 增长预估

内容 1,135 万字 → 32 MB，约 2.8 字节/字。按上游每年增长 10% 估算，DB 每年涨 3 MB 左右；图片数量少且已封顶上界。**80 MB 的预算能撑好几年。**

约束来自 App Store：蜂窝网络自动下载上限是 200 MB，我们远在其下，用户不会被拦。

## 降采样的实际效果

本次跑了 16 张超宽图（最宽 4049 px），全部收到 1600 px 以内。

**体积几乎没变**（9.8 MB → 9.6 MB）——因为其中大头是 PNG，无损重编码省不了多少。真正的收益在**解码内存**：4049×2265 的原图解码约 36 MB，缩到 1600×895 后约 5.7 MB，降了 6 倍。这正好对上 [0024](0024-performance.md) 里"大图导致内存尖峰"的风险。

## 重审条件

- App 超过 80 MB → 先查 DB 增长（内容本身），再考虑图片二次压缩。
- 上游开始大量配图 → 需要重新评估是否引入按需下载（但那与 0026 的完全离线冲突，届时再议）。

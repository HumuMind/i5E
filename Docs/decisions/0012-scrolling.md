# 0012 阅读交互：只做纵向滚动，不分页

状态：已定 · 2026-10-20

## 背景

I5。排版定了（[0011](0011-typography.md)：720 版心、19pt、一屏约 1,390 字），交互骨架还没定。

## 决定

**只做纵向滚动，不做分页。**

## 理由

1. **内容形态不适合分页。** 50% 的页面没有标题，读者是连续往下读的；970 行的速查表、长短不一的法术条目，分页后会切得很碎，还要处理表格跨页、图片放不下这些边缘情况。
2. **分页的成本全在边缘情况。** 断页必须在行边界上做（不能按像素裁，否则一行被切成两半）；字号变化、横竖屏切换都要全量重算，并把阅读位置映射回去。单人开发的性价比太低。
3. **可逆。** 滚动版先做，将来真要加分页模式不用推翻数据层——前提是位置模型别用滚动像素。

## 位置模型（关键约束）

阅读进度、书签、搜索结果跳转，一律用**内容定位**而不是滚动偏移：

```
(pageId, blockIndex, charOffset)   或   (pageId, anchorId)
```

这样字号变化、窗口尺寸变化之后位置仍然有效，将来加分页模式也不用改数据。用 `scrollOffset` 存进度是最省事也最容易后悔的做法。

## 后果

- 没有页码。进度用"全书百分比 + 当前章节名"，靠目录树反查当前位置。
- 左右各 152pt 的留白可以放竖向进度条与书签按钮——分页模式下这两侧基本只能空着。
- 滚动容器要处理长表格：单页最长 970 行，滚动性能必须实测。

## 重审条件

如果用户明确要求"翻页手感"，成本已知：行边界断页 + 重排 + 位置映射，约等于重做阅读页。这不会是个小改动，要单独立项。

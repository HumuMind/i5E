# 0004 内容包分两层：原文存档 + 阅读层

状态：已定 · 2026-10-20 · 部分取代 [0001](0001-content-model.md)

## 背景

要求：转换结果必须能完全还原成源 HTML，体积大一点可以接受。

**逐字节还原无法由 block 承担，这不是取舍问题。** HTML 再序列化一次，属性顺序、标签大小写、引号风格、自闭合写法、实体写法（`&amp;` 还是 `&#38;`）、以及 GBK 原始字节都会变。block 携带再多属性，也只能做到"语义等价"，做不到"字节一致"。要做到字节一致，唯一办法是保存原始字节。

所以问题不是"把 block 做成无损"，而是"原文放在哪一层"。

## 选项

- **A. 无损 block。** block 里带完整 DOM、全部属性、原文片段。体积 2–4 倍；渲染器要理解任意标签，等于在原生应用里重写一个 HTML 渲染器，与"不用 WebView 套壳"的初衷正面冲突。
- **B. 双层。** 原文原样存档，block 退化为可重建的阅读层。还原是恒等操作；体积增加约 30 MB（实测 tar.gz）。
- **C. 只存原文，运行时解析。** 等于把 [0002](0002-pipeline.md) 推翻成运行时方案：首启要处理 7207 个文件。

## 决定

采用 **B**（2026-10-20）。

内容包结构：

```
pack/
  source.tar.gz     原文，逐字节（保留原编码），事实来源
  manifest.json     path → {sha256, bytes}
  content.jsonl.gz  阅读层，block 序列，可从原文重建
```

三条规则：

1. **原文是事实来源，阅读层是缓存。** 两者不一致时以原文为准，阅读层随时可以整个丢弃重算。
2. **C8 校验闭环。** 从归档取出原文 → sha256 与清单一致 → 重新解析 → block 哈希与内容库一致。三条都通过，才说明"这块内容是那个原文的忠实派生物"。
3. **原文层不进 App。** 它服务于构建、审计、追新 diff 和"以后解析器改进后重跑"，不是阅读时需要的。要不要为"查看原文"功能随包分发，是独立问题（Q8）。

## 实测

| 项 | 大小 |
|---|---|
| 原文 HTML + 资源 | 102 MB（HTML 计）|
| `source.tar.gz` | 30 MB |
| `content.jsonl.gz` | 12.5 MB |

代价约 30 MB，换来的是"任何一页都能逐字节取回"，以及一个可以随时重跑的解析器。

## 后果

- 内容包不再是"转换结果"，而是"原文 + 派生视图"的组合。
- 阅读层的任何 bug 都不再是不可逆事故：丢掉重算即可。
- 追新可以只比原文层，diff 更干净（不掺解析器的变化）。
- 原文层要跟着发布存档走，仓库里不提交（生成物）。

## 重审条件

- 如果 App 需要"查看原文/引用原文"功能，原文层要从发布存档挪进 App，包体预算要重算。
- 如果上游开始提供结构化数据（而非 HTML），这层可以退役。

# 0026 内容更新：随 App 发版，不做内容包通道

状态：已定 · 2026-10-21 · 取代 [0002](0002-pipeline.md) 里"内容包分发层"的设想

## 背景

D4。[0002](0002-pipeline.md) 当初的设计是"构建期预生成 + 内容包留接口"，[0004](0004-source-archive.md) 也准备了内容包的形态。现在要决定：上游每周更新两三次，用户怎么拿到新内容。

## 决定

**这个 App 完全离线，内容随 App 发版。不做内容包下载通道。**

- 内容库 `content.db`（32 MB）与图片（9.6 MB）打进 App 包。
- 上游更新 → 重新构建 → 发新版 → 用户经 App Store 更新。
- 不引入任何网络请求，包括更新检查。

## 这意味着什么

| 项 | 结果 |
|---|---|
| 联网权限 | 完全不需要（外链跳浏览器是用户主动行为）|
| 隐私声明 | 可以写"本应用不联网、不收集任何数据"，这是一条很强的承诺 |
| 追新延迟 | 受 App Store 审核周期约束，通常几天 |
| App 体积 | 每次更新用户下载完整应用（App Store 自己做差分，不需要我们处理）|
| 内容版本 | `build-info.json` 里的 `upstreamCommit` / `contentVersion` 只作诊断用 |

## 与 0002 的关系

0002 说"内容包留接口，分发不做"。现在明确：**接口也可以不要**。

读取侧本来就只有一个"打开本地内容库"的路径，没有为下载预留任何状态机、版本协商或原子替换逻辑——这让代码少了一整类失败模式（下载中断、校验失败、版本不匹配、磁盘空间不足）。

如果将来真的要做内容更新，0002 和 0004 里的设计仍然有效，到时候再实现；但在那之前不预埋。

## 后果

- "定期追新"这个特性的含义变成"跟着版本更新"，README 里需要写清楚，避免让人期待每周自动同步。
- 包体成为唯一的成本约束——每次上游更新都会让 App 变大，需要在构建时留出余量（见 I20）。
- 审核说明里不需要解释网络行为。

## 重审条件

如果审核周期成为实际的追新瓶颈（比如上游每周更新而审核要一周），或者用户明确要求"不更新 App 也能拿到新规则"，再回到内容包方案。

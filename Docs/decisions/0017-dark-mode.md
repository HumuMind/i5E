# 0017 配色：跟随系统，对比度修复移植自上游

状态：已定 · 2026-10-21

## 背景

I10。源内容用颜色表达语义（标题暗红、术语绿、法术紫、物品蓝、怪物橙红），深色背景下 80% 的颜色会糊。

**一处需要澄清的事实**：内容仓库 `DND5e_chm/` 里**没有**深色模式；深色模式在包着它的 WebHelp 前端 `5echm_web_templates` 里。两者是不同的仓库，最初只查了前者，结论说错了。

## 上游怎么做的

两层机制：

1. **基础色用 CSS 变量，深浅两套**
   `--topic-bg` `#f4f5f7` / `#111315`，`--topic-surface` `#ffffff` / `#17191c`，
   `--topic-text` `#242629` / `#e7e9ec`，`--topic-accent` `#991b1b` / `#e16d6d`。

2. **内联颜色靠运行时对比度修复**（`webhelp-contrast.js`）
   逐元素算前景/背景对比度，不达标就朝黑或朝白混合，二分 18 步找到**刚好达标且离原色最近**的颜色。

关键点：它**不把颜色映射成语义 token**，只保证可读。所以 `#800000` 在深色下变成浅红，色相还在，而不是被换成灰色。

## 决定

- **跟随系统外观，不提供手动切换开关。**
- **对比度阈值 4.5:1**（WCAG AA，与上游一致）。
- **基础色直接采用上游那套值**，切换过来和网页版观感一致。
- **移植对比度修复**到 `ContentKit.Contrast`：纯函数、无 UI 依赖、有单测。每个 run 渲染时算一次。
- **表格底色**深色下用「向 surface 混合 0.88」压暗，保留色相与相对深浅（斑马纹、重点行仍可分辨）。

## 补记：样式表那一层颜色原来整个丢了

上线后发现「武僧」页的标题两种模式下都不是红色。查下来是分工问题：

**颜色有两个来源**——数据里的内联色（`#800000` 之类）和上游 `style.css` 的标签规则。我们只保留了前者。武僧页的标题没有内联色，红是浏览器套 CSS 套出来的，阅读模式一旦不套 CSS 就全黑。

同理丢掉的还有：

| 源规则 | 颜色 | 含义 | 影响 run |
|---|---|---|---|
| `h1,h2,h3` | `#800000` | 标题 | — |
| `h4` | `#704cd9` | 法术条目标题 | — |
| `h6` | `#0f5cbc` | 次级标题 | — |
| `U` | `#008000` | 术语 | 3,053 |
| `U EM`, `U I` | `#704CD9` | 法术名 | 6,098 |
| `B U`, `U B` | `#ee3300` | 怪物名 | 1,137 |

修法：把规则固化到 `SourceStyle`（ContentKit，可单测），渲染时「内联色 → 语义默认色 → 正文色」三级回退，然后统一走对比度修复。

教训：0011 写的是「颜色与字体族保留」，但实际只保留了数据层那一半。样式表是另一半，它不在数据里，也就没人想起来。

## 后果

- 颜色不再"照抄源页"，而是"照抄色相、修正亮度"。同一处在浅色与深色下呈现不同，这是预期行为。
- 对比度修复是逐 run 的纯计算，48,211 个带色 run 分摊到 7,187 页，开销可忽略。
- 表格底色压暗后，靠颜色区分的语义（如红色高亮单元格）会变淡，但相对差异还在。

## 重审条件

- 如果高频色（`#800000`、`#0000ff`、`#704cd9` 等）修复后"变味"太明显，给它们加白名单、直接指定深色值，而不是让算法算。
- 如果 4.5 在真机上显得偏灰，提到 7.0（WCAG AAA）会让颜色离原样更远。

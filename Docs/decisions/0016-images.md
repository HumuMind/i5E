# 0016 图片：只处理包里真有的，缺的直接不渲染

状态：已定 · 2026-10-21

## 背景

I9。源仓库的图片引用远多于实际文件：解析时统计到 575 处引用，其中只有 132 处能落到真实文件。剩下的是外部链接、Word/WPS 导出的本机临时路径（`file:///C:/Users/...`）、以及 CHM 模板自带的按钮图。

## 事实

| 项 | 值 |
|---|---|
| 能解析到的引用 | 132 处 |
| 去重后的文件 | 107 个 |
| 合计体积 | 9.6 MB |
| 丢失 / 外链 / 模板图 | 443 处 |
| 尺寸中位 | 372 × 210 |
| 最宽 / 最高 | 4049 × 2265；7 张高于 2000 |
| 宽于版心（720） | 31 张 |

## 决定

1. **只处理语料内、非模板目录的图片**。解析阶段就解析路径：找得到就把 `img` 改成语料内路径，找不到**直接丢掉这个 run**——不在数据里留死引用。
2. **打包时拍平成 `目录_文件名`**。Xcode 的 synchronized group 会把资源拍平复制进 bundle，保留目录结构不可靠；两端用同一个确定性变换（把 `/` 换成 `_`），不需要额外映射表。实测 107 个文件无重名冲突。
3. **缺图不渲染任何东西**。不留占位框、不显示 alt 文字——离线包里本来就没有，画个空洞只会干扰阅读。
4. **显示按宽度等比缩放**，最大宽度等于版心；高度不限，长图靠滚动。

## 后果

- 数据里少了 443 处图片引用。不影响 C1（图不是文本），也不影响 C5（两边都没有）。
- 包体增加约 9.6 MB，App 总大小约 59 MB（Debug 构建）。
- 解析结果变干净：`img` 字段现在只有两种状态——合法的语料路径，或者没有。

## 已知代价

大图按原尺寸解码。最宽的 4049 px 在 iPad 上解码约 36 MB 内存，虽然同一屏只有一两张，但极端页面会有尖峰。如果后面在真机上发现滚动卡顿，对策是**打包期降采样**（宽 > 1600 的缩到 1600），而不是在运行时压缩——那样每次滚动都要重算。

## 重审条件

- 真机滚动出现明显卡顿 → 打包期降采样。
- 上游补上缺失的 443 张图 → 解析逻辑不用改，下次构建自动收进来。

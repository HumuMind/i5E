# 0003 转换验证：证明"变化可解释"，而不是"内容正确"

状态：已定 · 2026-10-20

## 背景

每次从 `DND5e_chm/` 转换到内容库，都要回答一个问题："这次转换有问题吗"。7207 个文件全量跑一遍只要几分钟，成本不是障碍；障碍是"跑全量"和"证明正确"是两件事。

## 前提

- **没有标准答案。** 上游 HTML 是唯一事实来源，我们无法判断一句话对不对，只能判断它有没有被完整、如实地搬过来。
- **上游有错，我们不许改。** 所以"内容错误"不在验证范围内，发现可疑内容只记录、不修正。
- **上游是 git 仓库。** 每次同步有确切 diff，这给了我们一个不依赖标准答案的判据。

## 目标

不证明"转换正确"，证明**"两次转换之间的每个变化都能解释"**。可解释 = 要么上游确实改了那页，要么我们确实改了那行解析器。

## 检查

| # | 检查 | 判据 | 强度 |
|---|---|---|---|
| C1 | **字符守恒** | 页面可见文本（规范化空白后）必须逐字符出现在 block 序列里 | 硬性，全量 |
| C2 | **节点覆盖** | 每个 DOM 节点要么进入某个 block，要么命中忽略白名单；白名单出现新类型必须人工确认 | 硬性，全量 |
| C3 | **锚点与链接** | 所有 `id` 保留；内部 `href` 全部可解析；断链数量与基线比只减不增 | 硬性，全量 |
| C4 | **schema 校验** | 每个 block 通过 schema（必填字段、枚举值） | 硬性，全量 |
| C5 | **往返保真** | block 重新渲染成 HTML 后，与原页的「标签 + 文本」序列一致（DOM 规范化后比较） | 全量，允许白名单 |
| C6 | **回归哈希** | 上游未变的页，输出哈希必须不变；变了就是解析器回归 | 硬性，阻断 |
| C7 | **黄金样本** | 30–50 页覆盖各类结构（法术字段块、怪物 stat block、合并表格、图片、脚注、嵌套列表），解析器每次改动人眼过一遍 | 人工，每次改动 |

C1 是这套里最有价值的一条：吞内容是最常见也最难发现 bug，而字符守恒是纯机械可判的。它不需要知道内容对不对，只需要知道字没少。

C6 是免费的那条：它把"验证正确"降级成"验证没变"，后者是确定性的。

C5 是给 block schema 兜底的：切完再拼回去，形状不对说明粒度设计错了。

## 三种往返，别混为一谈

| 往返 | 成立吗 | 说明 |
|---|---|---|
| 源 HTML → block | **有损** | 实测单页只剩 5.9% 的体积，丢的是 Word 的样式噪音 |
| block → HTML → block | **恒等** | C5 测的就是这个：block 是我们自己的中间格式，必须是自己的不动点 |
| 源 HTML → block → HTML | **不等于原页** | 既不追求，也做不到 |

**从 block 还原不出原 HTML，这是设计而不是缺陷。** C5 也不证明这一点，它证明的是"预览里看到的就是 App 会拿到的"——否则预览会骗人。

保留：文本（逐字符）、段落切分、`h1`–`h6` 层级、`b/i/u/s/sup/sub/code`、链接 `href`、图片 `src`、锚点 `id`、表格行列与合并单元格、列表嵌套、引用、预格式化。

丢弃：`class`（197 种，一半是 `MsoNormal`）、`style`（46 万处、191 种属性，绝大多数是 `mso-*`）、`font/face`（13 万个）、颜色（276 种）、字号、对齐、宽度、`lang`、`script`/`style`、表单控件、注释。

**已知的语义缺口**：7187 页里有 3614 页（50%）完全没有标题块，其中 84 页正文超过 5000 字。Word 导出常把"小标题 + 正文"塞进同一个 `<P>` 用 `<BR>` 分隔，层级只由加粗和 `rgb(128,0,0)` 这类颜色表达（该颜色出现 31,792 次）。这些页面仍能读，但页内没有可导航的层次。C1 看不见这种损失——**它保证字没少，不保证层次对**。

## 决定

七条全部保留，C1–C6 已实现并全量跑通（2026-10-20，`Tools/content/`）：

| 检查 | 结果 |
|---|---|
| C1 文本守恒 | 7187 页全部通过 |
| C2 节点覆盖 | 无白名单外标签 |
| C3 锚点与链接 | 6929 条内部链接：可按语料根解析 6390，按文件目录 352，扩展名不符 16，断链 171；断锚点 152 |
| C4 schema | 通过 |
| C5 往返保真 | 7187 页全部通过 |
| C6 回归哈希 | 连跑两次零变化 |

C1 在实现过程中抓到四类真实缺陷，每一类都会静默破坏内容：

1. 条件注释 `<![if !supportLists]>` 的 tail 被重复处理 → 整句出现两遍（27 页）
2. 表格用 `iter("tr")` 展开 → 嵌套表格的行被算了两次
3. 被畸形标签挤出 `tbody` 的孤儿行 → 整行丢失
4. `<UL><UL><LI>` 畸形嵌套 → 整段列表丢失

这四类在预览里都不显眼，靠肉眼过样本很可能漏掉，C1 一次就报出来了。结论：所有检查里 C1 的性价比最高，**应当作为合并门槛，而不是发布前才跑**。

C3 的断链绝大多数是上游自带的（文件根本没提交），因此不能作为硬门槛，要改成基线化：数量只许减不许增。

## 后果

- 构建脚本的产出从"内容库"变成"内容库 + 验证报告"，报告作为构建产物留存。
- C1/C2/C4/C5/C6 作为合并门槛；C3 走基线比对。
- 需要长期维护三样东西：忽略白名单、黄金样本集（`Tools/content/golden-samples.txt`）、C3 基线。
- 这套检查覆盖不到"读起来舒不舒服"，那属于排版与交互决策，不在这里解决。

## 重审条件

- C1 误报率高到无法维护，说明空白与不可见字符的规范化规则要重订。
- 上游开始出现大批量结构性改动（而非文本改动），C6 的"没变就不许变"会频繁误报，需要改成按页分类判定。

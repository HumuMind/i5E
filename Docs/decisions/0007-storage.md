# 0007 存储与检索：单文件 SQLite + 单字双字索引

状态：已定 · 2026-10-20

## 背景

内容库是 56 MB 的 JSONL，是交换格式，不是 App 能直接读的东西。D3 要定两件事：存在什么里，以及中文怎么搜。

## 决定

1. **单文件 SQLite**，构建期生成，随包发布（`pack/content.db`）。
2. **表结构**：
   - `pages(id, path, title, style, css, blocks)` —— block 结构 zlib 压缩后存 blob
   - `search` —— FTS5，contentless，`detail=none`
   - `meta` —— 目录树、构建清单、格式版本
3. **分词：单字 + 双字预分词**，配 `unicode61`。
4. **查询三步**：候选召回 → 子串校验 → 够数即停。
5. **不带原文层**（Q8）：原文留在发布存档，App 只带阅读层。

## 为什么不是别的分词方案

实测（239,307 个文本块、1135 万字，真实建索引）：

| 方案 | 索引 | 2 字词（火球） | 3 字词（火球术） | 单字（龙） |
|---|---|---|---|---|
| `unicode61` 原样 | 27.4 MB | **0 命中** | 25 / 177 | 22 / 7191 |
| `trigram` | 67.4 MB | **0 命中** | 177 / 177 | **0** |
| 双字 | 45.7 MB | 237 / 237 | 177 / 177 | 1736 / 7191 |
| 单字+双字 `detail=full` | 68.0 MB | ✓ | ✓ | ✓ |
| **单字+双字 `detail=none`** | **27.8 MB** | ✓ | ✓ | ✓ |

`unicode61` 把一整段中文当一个 token，“火球”基本搜不到。`trigram` 对 2 字和单字完全无效，而中文两字词占大多数。

`detail=none` 是这里的关键：只存“这行有没有这个 token”，不存位置。位置信息是索引体积的大头，去掉之后比 `trigram` 还小一半多。代价是不能用短语查询——但我们本来就要做子串校验，短语能力用不上。

## 查询为什么分三步

双字索引会过匹配：搜 `AC` 时候选 10,283 行，实际命中 2,565 行。所以必须在候选集上做一次子串校验。

校验带来一个新问题：宽泛查询（如“的”，55,845 命中）如果把三千个候选全解一遍，要 570 毫秒。加**早退**——够 50 条就停——降到 3.5 毫秒。

## 实测

| 项 | 值 |
|---|---|
| `content.db` | 32.2 MB（pages 20.0 + search_data 10.8 + meta 0.8）|
| 建库耗时 | 约 4 秒 |
| 查询延迟 | 3.5–15 ms（limit 50）；limit 200 时 52 ms |
| 召回一致性 | C10：10 条探针查询，与内容库逐页比对完全一致 |

成本对比：阅读层 56 MB JSONL → 32 MB 单库。索引不是额外开销，是替代。

## 后果

- 客户端要复刻查询三步（拆词、拼 MATCH、校验早退），约 30 行 Swift。
- **结果按文档顺序返回，没有相关度排序**——`detail=none` 下 bm25 算不出词频。对阅读类应用可以接受：按书里的先后顺序列出来，比按"相关度"更可预期。
- 依赖 FTS5。启动时检查 `PRAGMA compile_options` 是否含 `ENABLE_FTS5`；不放心就用 GRDB 的自定义 SQLite 构建，行为确定但多几 MB。
- 增量更新只能整库替换（约 32 MB）。要分片得另做设计。

## 重审条件

- 如果用户抱怨"搜索结果顺序奇怪"，说明需要相关度排序，那就得换 `detail=full`（索引回到 68 MB）或另建一份带位置的索引。
- 如果 App 体积成为问题，优先砍 `blocks` 的冗余字段，而不是索引。

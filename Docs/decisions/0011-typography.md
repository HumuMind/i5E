# 0011 阅读排版：720 版心、19pt 正文、表格自适应

状态：已定 · 2026-10-20

## 背景

I4。数据里有颜色、字号、字体族，但阅读模式不能照搬——Word 导出的正文是 8–10pt，iPad 上没法读。要定的是版心、字号、对齐，以及表格怎么塞进去。

## 决定

| 项 | 值 |
|---|---|
| 版心 | `min(720pt, 屏宽 - 48)`，居中 |
| 正文 | 19pt，行高 1.8（34.2pt） |
| 对齐 | 两端对齐 + 标点禁则 |
| 表格 | 字号阶梯 19 → 16 → 13pt，下限 13；列宽与宽度规则已被 [0015](0015-table-layout.md) 取代 |
| 两侧留白 | 1024 宽屏上每侧 152pt，留给工具栏/书签/页码 |

## 为什么是 19pt

实测源仓库：82% 的页面没有设页级字号，设了的以 10.5pt、8pt、10pt 为主；按字数加权的有效基准 ≈ **10.1pt**（≈13.5px）。上游 `style.css` 只定义相对层级（h4 140%、h5 与 `P.sum` 115%），没有绝对字号。

19pt 相对 10.1pt 是 **1.42 倍**——"把 10pt 放大到能读"的比例。这个数字不是拍脑袋，是从源数据推的。

## 为什么是 720

中文正文舒适区间约每行 25–40 字。1024 宽下满宽排版是 48 字/行（19pt），偏宽；收到 720 后是 38 字/行，进区间。

代价是密度：一屏约 1,390 字，全书 1,135 万字 ≈ 8,100 屏。这个数字后面定分页/滚动时要用（I5）。

## 标题层级按用途，不按标签序号

上游的层级本身是乱的：`style.css` 把 `h4` 设成 140%，比 `h3` 还大，因为 h4 被用来做法术和怪物条目的标题。所以不按标签数字排序，按用途给：

| 用途 | 标签 | 相对正文 |
|---|---|---|
| 页标题 | h1 | 1.6 |
| 章 | h2 | 1.35 |
| 节 | h3 | 1.2 |
| 条目标题（法术/怪物名） | h4 | 1.25 + 保留源色 |
| 次级 | h5 / h6 | 1.1 / 1.0 |

## 表格为什么能够"不出格"

`table-layout: fixed` + `width: 100%` 意味着**任何表格都不会溢出**，列被压窄、内容换行。所以问题不是"放不放得下"，是"压到多窄还能看"。

实测 6048 个表格：列数以 2 列（3192）、1 列（1026）、3 列（484）为主，6 列 216 个，14 列 745 个。按内容自然宽度估算，**80% 在 13pt 以上就能舒服放下**，剩下 20% 需要靠换行。

13pt 是刻意留的下限：再小就不值得读了，宁可让换行变多。不做出格、不做横向滚动。

## 补记（2026-10-26）：改为左对齐

上线后在真实内容上发现两端对齐的硬伤：中文与英文/数字混排时，行内可拉伸的只有空格，
`NSParagraphStyle.alignment = .justified` 会把它们撑到极限，例如

> 警报将在其保护区域　60　尺范围内响起持续　10　秒的摇铃声。

字距被拉开后比右边不齐更难读。改为 `.natural`（左对齐）。

三条路里否掉了两条：只对纯中文段落两端对齐会造成同页内对齐方式不一致；
CJK 感知的两端对齐（按字距分配宽度）等于自己写文本布局引擎，成本与收益不成比例。

## 补记（2026-10-26）：字体改为无衬线

原文选的是宋体（衬线），理由是"长文阅读更稳"。但和源页逐页对比后，字体族是视觉差异最大的一项：
源页统一是无衬线（`font-family: Arial, Helvetica, sans-serif`，中文落到黑体/苹方）。

决定改为系统无衬线（iOS 上是苹方 + SF）。这样同一段文字在源页和 App 里的字形结构一致，
而不是"内容一样、气质不同"。

## 后果

- **不以源页绝对字号为准**是有意取舍——照搬 8pt 等于把 Word 的排版问题复制到 iPad 上。
- 颜色与字体族保留（0005 的 `c`/`fa`），绝对字号与对齐在阅读模式里丢弃。
- 深色模式下这些颜色怎么映射，是 I10 的事，不在本决策里。
- 手机端 `min(720, 屏宽-48)` 自动退化成满宽，不需要单独规则。

## 重审条件

如果实际阅读中"每屏 1,390 字"显得太稀、翻动太频繁，优先调版心（720→800）而不是缩字号——字号再小会掉出舒适区。

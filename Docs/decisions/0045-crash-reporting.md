# 0045 崩溃与反馈：不自建上报

状态：已定 · 2026-10-26

## 决定

**不做应用内的崩溃上报与诊断上传。**

## 能拿到什么

| 渠道 | 内容 | 前提 |
|---|---|---|
| App Store Connect 的崩溃报告 | 崩溃堆栈、设备型号、系统版本、发生次数 | 用户开启了「共享分析」|
| TestFlight 内置反馈 | 测试者的文字 + 截图 + 崩溃日志 | 已启用 TestFlight（暂未启用）|
| GitHub issue | 用户描述 + 版本信息 | 仓库公开 |

## 拿不到什么

- 崩溃前的操作序列
- 本地日志文件（离线应用没有上传通道）
- 未开启共享分析的用户的任何信息

这是"完全离线"（[0026](0026-offline-updates.md)）的直接代价，不是疏漏。

## 用什么补偿

既然拿不到现场，就把"事后能问清楚"做好：

1. **设置页显示版本**（[0039](0039-content-version.md)）—— 用户截图即可定位到具体的内容版本与应用版本。
2. **错误态写清楚**（[0040](0040-integrity-check.md)）—— 内容库读不出来时说明原因与出路，而不是白屏。
3. **页面打不开时显示路径** —— 交叉引用失效时能看到是哪一条，便于反馈。
4. **issue 模板要求填版本与设备**（[0044](0044-issue-template.md)）—— 把必要信息变成必填。

## 为什么不自建

自建上报需要服务器、隐私声明改写、App 审核说明，而且与"不联网、不收集任何数据"的承诺直接冲突——那条承诺是产品的一部分，不值得为一个便利的功能放弃。

## 重审条件

- 若崩溃率在 App Store 后台明显偏高（比如日活 1% 以上），再考虑接入 Apple 官方的 MetricKit（数据仍由系统汇总，应用不主动上传）。

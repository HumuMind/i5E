# 0043 上游同步流程

状态：已定 · 2026-10-26

## 决定

**一条命令完成同步**：`./Scripts/sync-upstream.sh`

它依次做：

1. 拉取上游 `DND5e_chm`（fast-forward；不是 ff 就停下让人处理）
2. 打印上游提交列表
3. 重建内容库（`run.py build --pack`）
4. 放进 App 资源目录
5. 数据层测试（34 个）
6. 格式检查
7. 构建 iOS 与 macOS

不改任何提交，确认后自己 commit。

只重建不拉取：`SKIP_PULL=1 ./Scripts/sync-upstream.sh`。

## 发版节奏

**上游有实质更新时才发版**，不按固定周期。

理由：固定周期会产生大量"只改了一句话"的构建，测试者疲劳、审核资源浪费；而上游本身约每周两三次提交，跟着它走更自然。

## 验证靠什么

| 层 | 检查 |
|---|---|
| 内容 | C1 文本守恒、C5 往返保真、C9 目录、C10 检索 |
| 数据层 | 34 个 Swift 测试 |
| 代码 | swift-format + swiftlint |
| 构建 | iOS Simulator + macOS |

这四项跑通才算同步完成。

## 为什么没有 CI

没有远程仓库、没有开发者账号，也就没有 CI 的落点。同步是本地单机流程，一条命令 + 人看结果，比搭一套没人维护的流水线可靠。

将来仓库公开、账号就绪后，再把同样的四步搬进 GitHub Actions 即可——脚本已经把顺序固定下来了。

## 版本号

- **内容版本**：构建时自动写进 `content.db` 的 `meta.build`（上游 commit、日期、提交标题），设置页可见。
- **应用版本**：手改 `MARKETING_VERSION`；构建号由 `Scripts/bump-build.sh` 从提交数生成。

# 0002 解析发生在哪一层：构建期预生成 + 内容包

状态：已定 · 2026-10-20

## 背景

同样的 HTML，可以在开发机上一次转好塞进安装包，也可以随包带原始 HTML、在用户设备上首启时再转。这个选择决定包体、首启耗时、追新成本和"解析器出 bug 时谁遭殃"。

## 事实

- 上游 7207 个 HTML、102 MB 正文，另含图片等资源，整体 427 MB。
- `DND5e_chm/` 是独立 git 仓库，有完整提交历史，可以 `pull` 拿增量。
- 单文件普遍很小（中位 3 KB），解析是**文件数密集型**而不是**单文件重型**任务。
- 构建耗时尚未实测，需要在 D1 定稿后用原型测一次。

## 选项

- **A. 构建期预生成。** 开发机／CI 跑解析器，产出数据库随 App 包发布。
  收益：首启秒开；解析器代码不进 App，出 bug 不影响已发布版本；App 里没有 HTML 解析逻辑，实现面小。
  代价：内容更新必须发版过审，追新节奏受 App Store 审核牵着走。

- **B. 运行时解析。** 随包带 HTML，首启在设备上建库。
  收益：不依赖构建机器，内容更新可以只换资源。
  代价：首启要处理 7200 个文件，冷启动体验差；解析器 bug 直接砸在所有用户头上；包体最大；低端设备上不可控。

- **C. 构建期预生成 + 内容包。** CI 解析产出内容包（单文件数据库），App 只读；更新走内容包下载，不走 App 更新。
  收益：首启秒开 + 追新不发版，两个问题一起解决。
  代价：多一套内容包的分发与版本协商；包和 App 的版本兼容要设计。

## 决定

采用 **C，第一版按 A 落地**（2026-10-20）。

- 第一版只做构建期预生成：构建脚本解析 `DND5e_chm/`，产出单文件内容数据库，随 App 包发布。App 内不包含 HTML 解析逻辑。
- 数据格式从第一天起带 `contentVersion` 与 `upstreamCommit` 字段，内容包当作"以后接的分发层"，**分发不做**。读取侧先抽象成"读本地内容包"一个接口，将来换成"读下载的内容包"时不动上层。
- 内容包将来的分发走 GitHub Releases 的静态文件：免费、无服务器、无需账号，符合"不加账号"的约束。App 侧只做「检查版本 → 下载 → 原子替换」，离线时继续用旧包。
- 构建清单（BuildManifest）与生成物都不进仓库。

## 后果

- 必须有一份构建清单（BuildManifest），记录上游 commit、解析器版本、内容包版本。否则"这份内容是哪个上游版本"无法回答。
- 生成物不进仓库（`.gitignore` 已有约束），意味着 CI 或本地构建脚本必须可复现。
- 若选 A 而永不接内容包，追新就永远等于发版，需要接受这个节奏。

## 重审条件

- 如果实测构建时间在可接受范围内且上游更新频率很低，内容包可以无限期推迟，A 直接作为终态。
- 如果 App Store 审核周期成为实际瓶颈（比如上游每周更新而审核要一周），内容包从"以后"变成"必须"。

# 0024 性能预算与基线

状态：已定 · 2026-10-21

## 基线（实测）

在 Mac（Apple Silicon，Debug 构建）上跑数据层基准：

| 操作 | 耗时 |
|---|---|
| 打开内容库 + 读出目录 | 25 ms |
| 单独加载目录（8.8k 节点） | 15 ms |
| 打开普通页（法术页 / 怪物页） | 1–6 ms |
| 打开 970 行参考页 | 81 ms |
| 搜索（50 条结果） | 76–114 ms |
| 全库正文哈希自检 | 3.9 s |

## 预算

| 场景 | 预算 | 依据 |
|---|---|---|
| 冷启动 → 目录可交互 | **< 500 ms** | 数据层约 40 ms，余量留给 SwiftUI 首帧 |
| 打开普通页 | **< 100 ms** | 数据层 1–6 ms，解码与排版占大头 |
| 打开 970 行参考页（卡片首屏） | **< 500 ms** | 数据层 81 ms + 首屏卡片渲染 |
| 搜索出结果 | **< 250 ms** | Mac 实测 110 ms，iPad 按 2× 估 |
| 全库自检 | **不阻塞启动** | 3.9 s 的量级，只能后台或按需 |
| 内存峰值 | **< 300 MB** | 32 MB 库 + 大图解码 + 970 行表格 |

## 已知的两处风险

1. **搜索 110 ms 偏高。** 瓶颈是逐页 JSON 解码（每个候选页都要解压 + 反序列化 + 拼接正文）。要降到 100 ms 以内需要引入页面文本缓存，但会多占内存。先按 250 ms 预算观察真机表现。
2. **全库哈希自检 3.9 s。** 这个功能只在测试里调用，App 启动时不跑。如果将来要在 App 内做数据完整性检查，必须放到后台线程且只在首次启动做一次。

## 打点

`Signpost.measure` 包了三处关键路径，用 Instruments 的 os_signpost 模板可见：

- `openDatabase` / `loadTOC`（冷启动）
- `loadPage`（每次翻页）
- `search`（每次搜索）

## 怎么测

1. 数据层：`CONTENT_DB=build/pack/content.db swift test --filter PerfTests`
2. App 层：Xcode → Product → Profile → Instruments 选 os_signpost，跑一遍冷启动、开大表、搜索
3. 滚动帧率：Instruments 的 Core Animation，看 970 行表格页

## 重审条件

- 真机上搜索超过 250 ms → 加页面文本 LRU 缓存。
- 冷启动超过 500 ms → 检查目录树解码（778 KB JSON）能否改为按需加载。

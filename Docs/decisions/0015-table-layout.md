# 0015 表格呈现：列宽按内容，不铺满版心

状态：已定 · 2026-10-21 · 修改 [0011](0011-typography.md) 中"表格宽 100%"的规则

## 背景

I8。[0011](0011-typography.md) 定了表格用 `table-layout: fixed` + 宽 100%，实现出来是**等宽列**。数据说明这个做法错得很明显。

## 事实

| 项 | 值 |
|---|---|
| 表格总数 | 6,048 |
| 两列表 | 3,192（最多）|
| 两列表中第一列内容占两列总宽 | **中位 2%** |
| 含合并单元格 | 1,038（17%），其中 colspan 998 个表、rowspan 仅 40 个表 |
| 单元格内含多段 | 116 个表 |
| 行数 | 中位 5；90 个超 50 行；最大 970 |

两列表里第一列（`1d6`、`AC` 这种）内容只占 2% 宽，等宽布局却分给它 50%，描述列被挤成一条。3,192 个表都长这样。

## 决定

1. **列宽按内容估算**：每列取单元格文本的显示宽度（CJK 算 2、其余算 1），上限 24 单位（12 个汉字），低于下限 6 单位（3 个汉字）抬到下限。
2. **自然宽度，不铺满**。内容窄就窄着，表格居中显示；只有在超出可用宽度时才等比压缩。
3. **支持 colspan**，被跨的列宽相加（998 个表）。
4. **不支持 rowspan**（40 个表，0.7%）：合并格渲染在首行，被覆盖的格子留空。能读，不完美，记在这里。
5. **长表行级懒加载**（最大 970 行），单元格内多段按块渲染。

## 为什么自然宽度

短表铺满会把两列各拉成 360pt，读起来中间空一大片。自然宽度下 `AC | 17` 就是七十来点宽，紧凑、也更像印刷品的表。

代价是右边留白，且不同表格宽度不一。这是有意的：表格宽度应当由内容决定，不是由版心决定。

## 实现

`TableLayoutCalculator`（ContentKit，纯几何、有单测）：

- `columnUnits` 按列取最大内容宽，colspan 格按跨列均摊
- `widths` 把单位换算成 pt，超宽时按比例压缩并保底
- 阅读区实际宽度由 `ReaderView` 用 `onGeometryChange` 量出来传下去，窄屏时自动收窄

## 后果

- 表格宽度随窗口变化重新计算，转屏与分屏下都合理。
- rowspan 的 40 个表会显示成"首行有内容、下方留空"，属于已知缺陷。
- 单元格里 116 个多段内容按块渲染，不再拼成一段。

## 重审条件

如果 rowspan 的 40 个表被反馈影响阅读，就补 `Grid` + 占位算法；如果用户觉得表格太窄、信息密度不够，再考虑加"紧凑/宽松"开关，而不是回到铺满。
